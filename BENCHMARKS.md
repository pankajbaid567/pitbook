# BENCHMARKS

Every number below is generated by `python3 scripts/make_benchmarks.py` from the raw files in `bench/results/`. Method and what is never claimed: [docs/benchmarks-method.md](docs/benchmarks-method.md). These are **laptop numbers for a single process**; they say nothing about the free-tier host.

## Environment

- CPU: Apple M3 (8 logical CPUs), 8 GiB RAM, darwin/arm64
- Go go1.25.4, GOMAXPROCS=8, commit `none`
- Conditions: power=AC Power; load_avg_at_start=4.07 4.12 4.04
- Source: `loadgen-20261110T105754Z.csv` (55 runs)
- The machine was a normal working laptop with other applications open (see the load average above), not a quiet benchmarking host; treat the numbers as indicative.

## Crash safety (`make crash-test`)

`cmd/crashtest`, report `crashtest-20261110T105312Z.json` (2026-11-10T10:55:40Z): **1000 runs, 0 failed**. Each run starts the real `pitbook` binary with a synchronous WAL, drives it with 4 concurrent HTTP clients, sends SIGKILL after a random 40–900 ms, restarts it and checks the recovered log against what the clients were told.

| check | count |
|---|---|
| acknowledged commands found in the recovered log, byte-identical to what was sent | 117,609 |
| fills seen by clients matched to the fill derived by replaying the log | 41,176 |
| commands in flight at the kill (no response received) | 4,000 |
| of those, already in the log without the client knowing | 1,892 |
| in-flight commands retried with the same client order id | 3,428 |
| retries answered *duplicate* (not logged twice) | 1,325 |
| runs where recovery used snapshot + log suffix (the rest replayed the log from sequence 1) | 64 of 1000 |

Environment: Go go1.25.4 on darwin/arm64, 8 CPUs. Seeds 1…1000, every failing seed can be replayed with `-seed N -runs 1`.

**Limits.** SIGKILL tests a *process* crash. The OS page cache survives it, so this does not test power loss or disk failure. Runs are short (a few hundred commands, a few seconds), so most recoveries replay the log from the start; the snapshot path is exercised in the runs listed above and in unit tests.

## Machine noise floor (control: `go run ./cmd/noisefloor`)

A plain spinning thread, no engine, no I/O, measuring the gaps between consecutive clock reads. Any stall here is the machine (scheduler, other processes, power management), not Pitbook. Tail latencies in the open-loop table cannot be read as better than this floor allows.

```
10s spin loop, nothing else running: stalls >1ms=12 >5ms=0 >10ms=0 >50ms=0 max=4.866583ms
10s spin loop, nothing else running: stalls >1ms=14 >5ms=6 >10ms=2 >50ms=0 max=16.315875ms
10s spin loop, nothing else running: stalls >1ms=7 >5ms=5 >10ms=1 >50ms=0 max=25.595375ms
```

## Matching core service time (`go test -bench BenchmarkSteadyMix ./internal/book`)

`Book.Apply` on the `steady`-style random mix, one goroutine, no queue, no log, no scheduler in the path: this is the cleanest number for the cost of matching itself.

- 5 runs of 3 s: **137 ns per command** (median; range 136 to 139 ns), i.e. about 7.3 million commands/s per core
- Allocation: see the `allocs/cmd` column above for the whole pipeline; the book itself allocates about one small object per resting order.
